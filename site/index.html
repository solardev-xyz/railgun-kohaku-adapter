00 / Review scope

A Railgun execution and custody layer
for Kohaku-compatible wallets.

Technical review dossier for Ethereum Foundation / Kohaku and Railgun engineers. This repository packages a restricted Kohaku-facing API, an authoritative Railgun account owner, a host capability contract and an independently installed reference wallet.

The implementation originated in Freedom’s wallet integration. Railgun’s engine, prover and circuits remain upstream cryptographic implementations. Our contribution is the composition around them: account enrollment, authenticated scan and wallet state, private preparation, supervised execution, retained signing custody, EOA submission journals, POI/TXID coordination and explicit recovery across process boundaries.

What we want reviewed

Whether the restricted plugin tier is useful within Kohaku; whether the owner/host split preserves the right authority boundaries; whether the Railgun state, POI and retained-operation composition is correct; and which contracts should be simplified or generalized before another team adopts it.

Independent adapter developed for Freedom. This is not an official EF, Kohaku or Railgun project site, and no endorsement is claimed. No integration audit or production-readiness claim. Repository review brief ↗

01 / Problem & implementation

Why a separate adapter, rather than a thin SDK wrapper?

Freedom needed an integration in which the wallet retains control of keys, storage, process lifetimes and egress. A prepare/send wrapper alone would leave the application to reconstruct Railgun account state, authenticate selected inputs, bind recipients, handle output POI and decide what a timed-out submission means. Those decisions are part of the spending authority boundary.

The work began in Freedom and was extracted with source provenance, then exercised by a standalone host that imports no Freedom source or profiles. It is more than an update to an existing plugin: this repository supplies the narrow plugin interfaces and the operational machinery underneath them. We do not claim a new protocol, a replacement Railgun engine or generic compatibility with every Kohaku host.

Upstream Rust continuation — October 13

ethereum/kohaku-rs is reintroducing Railgun, including an external signer and current POI artifacts. It is the preferred next backend candidate. We are contributing interoperability tests against the official Railgun engine and focused boundary fixes, while retaining this qualified JS implementation for comparison. The adoption assessment requires licensing/source approval, secret-lifetime controls, control of every network path, scoped POI disclosure and durable uncertain-send recovery before a switch. A proposed freedom-core contract keeps wallet authority separate from reusable protocol behavior.

02 / Kohaku interface boundary

Two integration tiers, with different callers.

Tier A: five restricted factories at the package root

CJS is canonical; the ESM wrapper re-exports the same function objects and operation registries. One physical package copy must own an operation and the broadcaster/submitter that consumes it. The root module is frozen and has exactly these five runtime exports.

FactoryResult / operation
createRailgunKohakuSnapshotPlugininstanceId, balance, notes and lifecycle; read-only host snapshot.
createRailgunKohakuPrivateAdapterReads + prepareTransfer/prepareUnshield; opaque private operations.
createRailgunKohakuPrivateAdapterBroadcasterbroadcast(operation) from the same genuine adapter.
createRailgunKohakuPublicAdapterReads + prepareShield; opaque public operation.
createRailgunKohakuPublicAdapterSubmittersubmit(operation) for that adapter’s public operation.

The reference wallet composes these factories over genuine owner lanes. The root private input is one ERC-20 note with asset, amount: bigint and noteId; transfer binds a Railgun recipient, unshield a public recipient. Public Shield is native-only. Supported proof shapes and deployment remain narrow.

Private preflight selects 01x01 for a full transfer/full unshield and 01x02 for partial unshield with change or the local relay path. The input count is one; multi-input transfer/consolidation is not supported by this interface. Local relay preparation is not authentic relay transport qualification.

Private submission outcomes distinguish an acknowledged direct transaction, { transactionHash, submissionStatus: "unknown" }, and { status: "recovery-required", stage }. A failure-shaped result is not permission to prepare or broadcast a second payment. Read projections retain unverified provenance; frozen DTOs and TypeScript brands cannot replace runtime ownership checks.

Illustrative composition — capabilities already authenticated

  createRailgunKohakuPrivateAdapter,
  createRailgunKohakuPrivateAdapterBroadcaster,
} = require("@freedom/railgun-kohaku-adapter");

const adapter = createRailgunKohakuPrivateAdapter({
  host: genuinePrivateLane, // issued by this account's owner session
  signal,
  maxAmount: capturedAmountCeiling,
});
const operation = await adapter.prepareTransfer(ownedInput, bobRailgunAddress);
const outcome = await
  createRailgunKohakuPrivateAdapterBroadcaster(adapter).broadcast(operation);

Enrollment, wallet opening and original owner/EOA reviews are omitted. This illustrates composition, not turnkey signing. A root maxAmount cannot override the owner’s captured policy.

Tier B: the complete owner at /host/owner

initializeRailgunMain({ host, runtime, applicationPolicy?, deployment? }) returns createAccount and openAccount. Session lane constructors are openRead, openPrivate, openPublic, openRecovery, openPoiRecovery, openSubmissionRecovery, openShieldRecovery, openRelayLocal and openRelayRecovery. Main initialization is one-shot, including a failed/preempted attempt; separately initializing /host/execution in that realm is unsupported.

The safe /data capsule reader and /read projections grant no account/spending authority. Trusted /host/* entries expose documented composition helpers; arbitrary src/** imports are not a supported integration surface.

Kohaku compatibility claim

The recorded bridge checks restricted plugin specializations and the broadcaster shape. Generic Kohaku Host/CreatePluginFn integration is not claimed. Published types are self-contained; the pinned upstream package is a development-only bridge dependency, not a runtime dependency.

Credential schedule and loan lifetime

The master BIP-39 seed stays inside the host vault. Owners receive scoped, owned 32-byte material for spending-public, spending-sign, viewing or storage-root. No generic derivation callback or caller-selected path crosses the boundary.

The hardened Baby Jubjub schedule uses spending m/44'/1984'/0'/0'/index' and viewing m/420'/1984'/0'/0'/index'. Storage-root derivation binds profile identity, account index, chain and deployment. Historical Freedom domain strings are compatibility contracts, not cosmetic names.

Loans validate genuine context, purpose, vault session and currentness; retain original native callback promises; wipe borrowed bytes on revocation/settlement. Unknown signing-child exits keep the stable account excluded. The revoked storage-root drain is teardown-only, not credential admission.

Exact derivation/admission contract ↗

Cancellation, original settlement and process exclusion

Revocation stops new authority before work necessarily settles. closed covers original requests, children, storage work and key loans. A timer-raced replacement Promise or kill request is not observed closure.

Failed/unobservable drain keeps the account excluded. Reviews must settle on their supplied signal and return the exact result or an original native same-realm Promise. Custom thenables are not assimilated; unknown settlement conservatively quarantines the account.

Electron MessageChannelMain, utility parent ports and ASAR loading are actual runtime requirements. Node child-process IPC is not a substitute. Node API evaluation does not qualify a Node-only owner host.

Contracts: call-site inventory · context/storage · owner declarations · host assembly

Threat model and remaining trust assumptions

Trusted: application main, vault, captured callbacks, local context/guard issuance, source baseline and verified runtime immutability. This does not defend against a malicious host or compromised main process.

Handled with bounded validation/custody rules: malformed/inconsistent service data, stale evidence, cancellation, process death, uncertain delivery and authenticated-store tamper/downgrade cases. Source measurement and encrypted floors are not a blanket defense against an adversary controlling the host filesystem and key authority.

Residual: coherent dishonest RPC views are not independently chain-verified; POI/TXID assertions retain documented service trust. Network observers, direct EOAs, funding and aggregator disclosures can link activity. Circuit isolation and relay privacy need separate evidence.

04 / Operation custody & recovery

Preparation, an attempt and an observation are different states.

Preparation binds the owned input, nullifier, destination, value and capsule. Authenticated source/POI/TXID checks and supervised proving produce a retained operation. EOA review/submission are separate. The saved guide and readable notes never substitute for genuine owner authority.

Submission recovery exposes describe(holdId), observe(holdId) and resolve(holdId, { minimumConfirmations }). Description reads local authenticated custody. Observation reviews disclose public submitter, transaction identifier, nonce reconciliation and timing. The join uses exact signing intent/nullifier/tree/operation against current and archived journal state, not the last transaction row.

Live recovery case

Bob’s warm EOA review expired after a genuine proof was retained. An initial cold disclosure review also expired. Later observations found the same proof-present, unjournaled hold; the owner’s openRecovery().submitStored reused the original private spending signature with a fresh EOA review. Root adapters carried his initial warm preparation, not that cold broadcast; openSubmissionRecovery provides local description, observation and resolution. One unshield transaction resulted, without a new private proof or mid-run installed-code change.

Shield reviews additionally check fresh nonce, balance, estimate and simulation after the human reply. A changed transaction is refused rather than silently re-signed under the old approval. The updated submission protocol is a separate adoption obligation for Freedom.

05 / POI / TXID integration

Proof validity, service response and owned-output eligibility are separate.

Owners synchronize public TXID state into a journaled local mirror, validate roots through the configured services, reconstruct own-input membership and prove output POI with pinned artifacts. Submission serializes the retained payload, independently validates it in a keyless process and writes an attempt before transport. Raw proofs and internal receipt constructors do not cross the operational lane.

POI_3x3 public inputs and the independent verification job

The keyless offline job derives eight public signals from the normalized submitted payload, in the pinned circuit order: [bc0, 0, 0, txidRoot, unshieldMarker, poiRoot0, Z, Z]. Blinded-output padding is zero; Z is the pinned engine Merkle zero used for POI-root padding. The key must have nPublic: 8.

The pinned serial verifier must accept the payload and reject a changed TXID-root signal. Transition mode instead requires completed retired-positive, retired-negative-control and current-negative verdicts; thrown verification or exit failure refuses. The job imports no engine, account, store or key.

List/checkpoint metadata is bound in the payload digest, not authenticated by the circuit. Its result explicitly leaves source/membership/root acceptance, disclosure and spending authority false. Later controllers establish those separately.

V4 adds a consumed retry reservation; V5 appends replacement payload/proof history without rewriting original entry/attempt/retry. Replacement selection requires exactly one attempted intent for the hold, a consumed retry, one output commitment and no replacement attempt. Old readers refuse these documents; rollback cannot strip a reservation to regain authority. These are narrow reviewed transitions, not a generic reset or unlimited POI retry API. The normal saved guide does not automatically invoke them.

Historical circuit incident

Earlier handoffs used a pinned retired POI_3x3 circuit. A live transition check established that the original proof verified under the retired key and failed under the current key; a current-circuit replacement was later observed Valid. The deployed verifier revision and first rejected response body were not observed. This does not qualify future rotations.

In the frozen Alice/Bob guide, one HTTP 200 handoff response was classified malformed; the body was not retained or reconstructed from its size. Bob independently observed Valid with accepted roots and verified membership. That service-reported owned Valid status, with accepted roots and locally verified membership under unverified service trust, is the acceptance evidence. HTTP success and local recovery match do not suffice.

Availability recovery is public-TXID-only

The reference txid-sync permits two classified transport recovery continuations, ten seconds apart, under original consent, a ten-minute deadline and an 80-call budget. Genuine process-local provenance must classify connection/timeout; RPC errors, rejected roots, malformed/non-200 replies, cancellation and failed cleanup do not qualify. Two consecutive segments without returned count progress stop. Each reopened owner authenticates its pending page/checkpoint; no fabricated cursor.

Scan recovery stays explicit. Selected POI membership/status, proving, signing, POI handoff and broadcast do not inherit this loop.

Complete attestation versus derived-cache compatibility

The complete immutable snapshot measures every enrolled package file and the host inventory before owner algorithms load. Public, wallet and TXID caches use separate compatibility domains with new sources included by default. The sole current package exclusion is the POI serializer/response classifier, which does not interpret those caches. Reference host exclusions cover terminal presentation/manifest bytes; startup, commands, transport, storage and runtime selection stay bound.

readCacheDigests() must describe the same snapshot as readDigest(); omission retains full-host invalidation. The split invalidated earlier derived generations once, with no silent conversion. A serializer edit changing attempted body bytes still fails retained-body normalization even when cache compatibility is unchanged.

Format interpretation is independent of the current ceiling

Legacy transfer/full-unshield capsules remain v1, partial-with-change v2; canonical wider internal capsules use v3/v4. Historical safe readers keep their contracts. Public journal versions depend on public calldata amounts, never a transfer’s hidden input value. A lower policy does not hide older notes/custody; it refuses new spending. Rebuilding caches cannot reset attempts, floors or original signatures.

Read scheduling overlaps independent deployment/artifact/fee/verifier work with POI/TXID checks. Selected root-history/nullifier reads wait for genuine eligibility receipts. Existing receipt ages, review floors, send reserve and destination checks are not renewed by this overlap.

07 / Independent reference application

The host is a separate application, not a callback mock.

examples/reference-wallet/ is a headless Electron CLI with its own vault, stores, profile locks, contexts, supervised processes, Tor transport, signer and journal. It installs the real packed tar/whitelist; no Freedom source/profile is imported. Alice and Bob use independent random seeds, funding EOAs, Railgun identities, stores and fresh processes.

  1. Alice: Shield

    Root public adapter/submitter over genuine owners. Settlement + scan/wallet refresh select the private input bound to that Shield.

  2. Alice: foreign private transfer

    Root private adapter/broadcaster; Bob’s address bound before proof/signing. Settlement matched against the original hold/journal.

  3. Alice: output POI

    TXID mirror/source membership feed retained POI. Reviewed handoff covers Bob’s output; Alice cannot certify Bob’s status.

  4. Bob: independent discovery/eligibility

    His scan/wallet find the exact note; his TXID store and owned Valid observation support subsequent owner checks. No key/database exchange.

  5. Bob: unshield/accounting

    Prepare or recover the original operation; fresh review, sign/send, finality. Three receipts, gas bounds, value conservation and available-note residuals.

The encrypted guide chooses steps deterministically and invokes original owner reviews. Each journey-next is one explicit step, not an unattended transaction/POI loop; no LLM is in the state machine. An AI agent operated the live callbacks. Operator wrappers changed outside the frozen install and their per-invocation source versions were not captured; original reviews/results and the accounting verifier are sealed in private evidence.

Privacy/trust boundary

Direct EOA funding/submission create public links. The guide exchanges a payment transaction identifier with Bob; that information is linkable. Dedicated Arti routing does not establish circuit isolation. Observations/finality retain unverified-rpc; no light-client path is claimed.

Acceptance roadmap · human tasks · release gates

11 / Requested review

Questions that would change the design.

EF / Kohaku engineers

  1. Is this restricted plugin/private/public/broadcaster tier useful, or should the adapter implement a different standard composition point?
  2. Which opaque operations and uncertainty outcomes belong in a reusable Kohaku interface rather than a wallet-specific owner?
  3. Which host families should become reusable capabilities? Where would simplification remove necessary identity, lifetime or signing constraints?
  4. Which generic host/factory tests should precede wider compatibility claims beyond the recorded structural bridge?

Railgun engineers

  1. Does Shield-/Transact-origin provenance, TXID mirror/root validation and owned-output POI preserve the engine’s intended invariants?
  2. What supported circuit/service compatibility signal should a wallet use before proving/submitting? Which deployment behavior can be relied on beyond the pinned source?
  3. Are identical retries and retired-circuit replacements scoped correctly? Which duplicate, historical-root and request/response semantics should be modelled?
  4. Which retained data and nullifier/journal joins are essential to cold submission? Which conservative compatibility restrictions can be narrowed with evidence?

Wallet implementers / security reviewers

  1. Can you replace the host without private instructions? Which capability, native dependency or runtime setup step is impractical?
  2. Where do cancellation, unknown exit, rollback, expired review or uncertain delivery permit an unsafe inference—or an unnecessary availability failure?
  3. Which evidence is missing for experimental adoption, and which separate evidence would be required for production?
